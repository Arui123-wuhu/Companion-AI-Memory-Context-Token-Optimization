# 设计说明

本文解释 CAIM 为什么这样设计、关键公式从哪来、以及在哪些地方做了取舍。

## 1. 出发点：上下文是工作记忆，不是硬盘

LLM 的上下文窗口在工程上经常被当成"记忆"，但人脑不是这么工作的：

- **工作记忆**容量极小（7±2 个组块），只放"此刻正在处理"的信息；
- **长时记忆**容量近乎无限，但需要**线索**才能提取；
- 两者之间靠**巩固**（consolidation）和**遗忘**（forgetting）维持平衡。

所以正确的问题不是"怎么把更多历史塞进上下文"，而是
**"此刻最该被想起的 5~10 条信息是什么"**。CAIM 的每个模块都服务于这个判断。

## 2. 记忆分类

| 类型 | 语义 | 初始 importance | 是否置顶 |
| --- | --- | ---: | --- |
| `PROFILE` | 身份、称呼、长期特征 | 0.95 | 进核心档案 |
| `PROMISE` | 承诺、约定、待办 | 0.85 | 否 |
| `FACT` | 客观事实 | 0.70 | 否 |
| `PREFERENCE` | 偏好、喜恶、忌口 | 0.65 | 否 |
| `EVENT` | 情景记忆 | 0.30 | 否 |

用户显式说"记住……"时，抽成 `pinned=True` 的 `FACT`，importance=1.0，**永不参与修剪**。

## 3. 遗忘：为什么是指数衰减

艾宾浩斯遗忘曲线可写为 `R = e^(-t/S)`，其中 `S` 是记忆强度。CAIM 用半衰期形式：

```
R(t) = strength · 0.5^(Δt / half_life)
half_life(importance) = 2 + 40 · importance^1.5    # 天
```

- 取 2 天为下限：闲聊如果不被回忆，一周内自然淡出；
- 取 42 天为上限：重要事实不会因为"很久没提"就消失；
- 指数 `1.5` 让中等重要度（0.6~0.8）的记忆明显比闲聊更持久，又不会全都变成"永久"。

**间隔重复**：每次被检索命中，执行

```
strength ← strength + 0.3 · (1 - strength)
last_access ← now
```

增量与剩余空间成正比，因此强度渐近于 1，不会溢出；同时重置衰减起点。
这模拟了"每次想起都更牢"的 spacing effect。

## 4. 检索：为什么近因权重这么低

```
score = 0.55·relevance + 0.12·recency + 0.23·importance + 0.10·strength
```

很多 RAG 系统会给 recency 很高权重（0.3+），但陪伴场景里这会让**最近的闲聊**压过
**三个月前的过敏信息**。而"最近的对话"本来就会以原文进入上下文（`最近对话`段），
近因需求已经被满足；长时记忆的职责是补"久远但重要"的信息，所以：

- relevance 最高（0.55）：先保证"问什么找什么"；
- importance 次之（0.23）：过敏、生日、承诺天然优先；
- recency 最低（0.12）：只用来在同等相关时打破平局；
- strength（0.10）：常被想起的略微占优。

`relevance` 用字符二元组覆盖率，并做同义词扩展（讨厌/不喜欢/不吃、忌口/过敏）。
扩展词只增加命中、不扩大分母，避免"扩展越多分越低"。

**MMR 去冗余**：`score - 0.25 · max_sim(已选)`。同一件事的多种说法不会占掉多个名额。

## 5. 上下文装配：预算是硬约束

```
┌───────────────────────────────┐
│ rules        ~40 tokens 固定  │
├───────────────────────────────┤
│ 核心档案     ≤28% 剩余         │  置顶 + PROFILE
├───────────────────────────────┤
│ 长期记忆     ≤50% 剩余         │  检索 top-k
├───────────────────────────────┤
│ 最近对话     剩余（≥1 轮）      │  原文
└───────────────────────────────┘
```

不变量（有测试覆盖）：

1. 最终 `tokens ≤ budget`，预算再小也不崩；
2. 置顶记忆至少保留一条，哪怕预算只够一行；
3. 同一条记忆不会同时出现在"核心档案"和"长期记忆"；
4. 最近对话至少保留一轮，保证对话不"断片"；
5. 预算富余时不强行填满——相关记忆装完就停。

## 6. 巩固：三个动作

| 动作 | 触发 | 效果 |
| --- | --- | --- |
| 去重 | 相似度 > 0.85 且同类型 | 合并为一条，强度/重要度取大 |
| 情景压缩 | 情景记忆早于最近 24 轮，每 4 条 | 压成 1 条"阶段纪要" |
| 修剪 | 有效强度 < 0.06 且类型为 EVENT | 删除 |

压缩后的纪要仍是 `EVENT`，因此**可以反复压缩**（progressive summarization），
存储量随对话增长呈对数而非线性。

## 7. 扩展点

| 想换什么 | 怎么做 |
| --- | --- |
| 抽取器 | 实现 `Extractor` 协议，返回 `list[Memory]`；`memory_from_llm_json` 可直接复用 |
| 相关性 | 替换 `retrieval.relevance`，或给 `score_memory` 增加 embedding 项 |
| 存储 | `MemoryStore` 是薄封装，换 Postgres/Redis 只需实现同名方法 |
| 装配策略 | 继承 `ContextBuilder` 覆写 `build`，配额常量在模块顶部 |

所有扩展点都保持"核心零依赖"，方便嵌进已有 Agent 框架。

## 8. 明确的取舍

- **不做向量库**：陪伴场景记忆量 10²~10⁴，线性扫描足够；换来零依赖、可离线、可解释。
- **不自动调 LLM 抽取**：默认规则抽取免费且确定；需要更强语义时再显式接入，避免悄悄产生费用。
- **不做记忆冲突消解**：目前"我搬家了"不会自动覆盖旧城市，这是已知缺口（见路线图）。
- **token 用估算而非精确分词**：为了零依赖；对预算控制来说 ±15% 足够，计费场景请开 tiktoken。
