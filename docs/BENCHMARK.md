# 基准报告

> 复现命令：`caim bench` / `python benchmarks/run_benchmark.py --sweep`

## 1. 方法

### 数据

- **对话**：`src/caim/benchmark.py` 用固定种子生成，无随机性，任何人跑出的数字一致。
- **埋点**：12 条关键事实分布在 120 轮对话的第 3~97 轮，覆盖名字、生日、过敏、宠物、
  城市、职业、恐惧、乐队、家人、忌口、约定、显式"记住"。
- **噪声**：其余轮次从 20 条日常闲聊中循环取样，制造真实对话里的语义干扰。
- **时间**：每轮推进 3 小时（120 轮 ≈ 15 天），让遗忘曲线真实生效。

### 三种策略

| 策略 | 定义 |
| --- | --- |
| 全量历史 | 所有轮次原文 + 系统约束 |
| 滑动窗口 | 最近 10 轮原文 + 系统约束 |
| CAIM | `MemoryEngine` 按预算装配（默认 1200） |

### 指标

- **上下文 tokens**：用 `caim.tokens.estimate_tokens` 统一估算（中文 1 字 ≈ 0.95 token）。
- **关键事实保留**：对每条事实构造一个探针问题（"我有什么食物过敏？"），
  单独装配一次上下文，检查判定关键词（"花生"）是否出现在上下文里。
  12 条探针全中记 12/12。

> 这是一个**可解释的代理指标**：它回答"模型有没有机会看到这条信息"，
> 而不是"模型最终答得对不对"（后者需要 LLM 评判，见第 5 节）。

## 2. 主结果

**120 轮，预算 1200：**

| 策略 | 平均 tokens | 节省 | 事实保留 |
| --- | ---: | ---: | ---: |
| 全量历史 | 2,768 | 0% | 12/12 |
| 滑动窗口（10 轮） | 264 | 90% | 0/12 |
| **CAIM** | **279** | **90%** | **12/12** |

滑动窗口体积和 CAIM 接近，但关键事实全丢——因为它只保留最近 10 轮，
而事实埋在前面。这正是"省 token 但失忆"的典型。

**规模扩展（预算 800）：**

| 轮数 | 全量 | CAIM | 节省 | 事实保留 |
| ---: | ---: | ---: | ---: | ---: |
| 120 | 2,768 | 279 | 90% | 12/12 |
| 400 | 9,069 | 280 | 97% | 12/12 |
| 1000 | 22,570 | 280 | 99% | 12/12 |

CAIM 的上下文大小**基本不随对话增长**（279 → 280），因为增长的只是长时记忆库，
检索始终只取最相关的一小撮。

## 3. 预算扫描（400 轮）

| 预算 | CAIM tokens | 事实保留 | 预算使用率 |
| ---: | ---: | ---: | ---: |
| 200 | 185 | 12/12 | 93% |
| 300 | 280 | 12/12 | 93% |
| 600 | 280 | 12/12 | 47% |
| 1200 | 280 | 12/12 | 23% |
| 2400 | 280 | 12/12 | 12% |

预算超过约 300 后，上下文不再增长：高相关记忆已经装完，**实现会选择停下，而不是塞噪声**。
如果业务上更看重召回（宁可多给模型一些背景），把 `ContextBuilder.build(top_k=...)` 调大即可。

## 4. 消融：巩固到底有没有用（400 轮，budget=800）

| 巩固 | 记忆条数 | 存储 tokens | 上下文 tokens | 事实保留 |
| --- | ---: | ---: | ---: | ---: |
| 开 | 31 | 426 | 280 | 12/12 |
| 关 | 402 | 4,605 | 279 | 12/12 |

- 巩固把**存储**压掉 **91%**（4,605 → 426 tokens），关键事实一条不少；
- 对**单次上下文**几乎没有影响（280 vs 279）——它的价值在长期：记忆库不膨胀，
  检索扫描成本、备份体积、迁移成本都更低；
- 关掉巩固时，1,000 轮后记忆库会到 ~12k tokens 且全是低价值情景，检索噪声显著上升。

> 这也是为什么 CAIM 把巩固放在"存储侧"而不是"每次都重新摘要"：
> 巩固是一次性的整理成本，摘要若放在每轮推理里，会持续烧 token。

## 5. 这个基准测不到什么

诚实地说，它有三个明显局限：

1. **关键词匹配 ≠ 正确回答**。上下文里有"花生"不代表模型会正确回答"你对花生过敏"。
   严谨做法是用 LLM 打分（如 1~5 分相关性），但会引入模型偏差与成本，不适合放进 CI。
2. **合成数据偏干净**。真实对话有指代（"那个东西"）、纠错（"不是杭州，是苏州"）、
   多话题交织，规则抽取的召回会明显低于基准。
3. **token 估算是近似值**。中文 1 字 ≈ 0.95 token 是经验值，真实分词器（DeepSeek/Qwen/GPT）
   会有 ±15% 差异。绝对值可能漂移，但三种策略用同一口径，**相对节省比例是可信的**。

## 6. 复现

```bash
pip install -e .
caim bench --turns 120 --budget 1200
caim bench --turns 400 --budget 800 --json
python benchmarks/run_benchmark.py --sweep
python -m unittest discover -s tests -v
```
